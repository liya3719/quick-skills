IRON LAW：**五文档未确认前 0 行实现代码；确认后须可回滚。无已落地 v1、v2…时，用例须能证明相对源代码等价；已有 v1…时，须证明相对「源代码 + 方案冻结的参考版 v{n}」双线无未记录偏离。**

# refactor-module — 独立 / 链路模块重构

**版本记号**

- **源代码模块**：重构前的既有实现（原包/原目录）；**禁止在其上原地大改**冒充重构完成。
- **v1、v2、…、vn**：在源代码之上**落地**的重构迭代；**vn** 为本次要归档/交付的第 n 版实现目录或开关态。
- **基线怎么定（防漂移）**
  - **尚无已落地 v1、v2…时**：仅以 **源代码模块** 为基线；等价断言、回归与契约说明只对照源代码。
  - **已有已落地 v1、v2…时**：以 **源代码模块** 与 **技术方案中写明的参考版 v{n}**（通常为上一已冻结/已发布实现；n 必须写死）**双线**作为对照基线；新实现不得相对任一锚点产生未写入文档的偏离；若两锚点对外预期本应一致却测出不一致，须在方案中排查并记录裁决，不得静默改一侧。
- 路径 `refactor/{模块名}/{vn}/` 的 `{vn}` 为本次工作目录版本名（首版落地也常为 `v1`）。

## Iron Law（铁律）

**功能逻辑等价 + 五文档（现状与风险、调用图、三主文档）未确认前 0 行实现代码。**

- 不改变对外可观测行为、错误语义、时序与并发承诺（除非用户书面批准并全量更新契约与用例）。
- 禁止在**源代码（原业务路径）**上原地重写；必须 **源代码与目标 vn 实现路径（及需保留的 v1…v(n-1)）并存** 与可操作的**回滚开关**。
- 禁止顺手优化与本次重构无关的代码、命名或全仓格式化。
- 《技术方案》《重构计划》《测试用例》及步骤 2 所列 references 未经确认前，禁止创建或修改实现代码。

## 执行前自问（写入技术方案或回复摘要）

- 当前仓库**是否已有落地**的 v1、v2…？若无：等价与用例是否**仅**锚定源代码？若有：方案中写死的 **v{n}** 是哪一版、路径/开关态是什么？
- 对外契约相对 **源代码** 如何满足？若启用双线，相对 **v{n}** 如何满足？是否存在未写入文档的差异？
- 哪几条用例分别覆盖「源代码锚点」「v{n} 锚点」（若适用）？回滚后是否回到方案声明的锚点组合？

## 前置依赖 ⛔ BLOCKING

在支持插件的 Claude Code 环境中，优先用 `understand-anything` 完成代码理解。若未安装：

```bash
/plugin marketplace add Lum1104/Understand-Anything
/plugin install understand-anything
```

安装后执行 `/understand`（或项目约定等价命令），再继续。

无插件环境：在回复中列出已读关键路径/文件与仍不确定项，**不得**跳过理解直接改代码。

## 工作流 Checklist

复制并逐项勾选：

```
- [ ] 0. 代码理解 ⛔ BLOCKING（understand-anything 或等价）
- [ ] 1. 与用户对齐 ⚠️ REQUIRED：模块名、**源代码路径/包名**、是否已有落地 v1…（无则基线仅源代码；有则写明**参考版 v{n}** 与源代码双线）、本次目标版本号 **vn**（v1、v2…中落档哪一版）、独立或链路模块
- [ ] 2. 重构前文档与 references
  - [ ] 2.1 现状与风险 → refactor/{模块名}/{vn}/references/现状与风险.md（模板：references/现状与风险模板.md）
  - [ ] 2.2 调用关系图（Mermaid）→ refactor/{模块名}/{vn}/references/调用关系图.md（模板：references/调用关系图模板.md）
  - [ ] 2.3 《技术方案》→ refactor/{模块名}/{vn}/技术方案.md
  - [ ] 2.4 《重构计划》→ refactor/{模块名}/{vn}/重构计划.md
  - [ ] 2.5 《测试用例》→ refactor/{模块名}/{vn}/测试用例.md
  - [ ] 2.6 技术方案、重构计划、测试用例与现状与风险、调用关系图之间条目可追溯一致 ⚠️ REQUIRED
  - [ ] 2.7 CONFIRMATION GATE ⚠️ REQUIRED：未得明确肯定前禁止改实现代码
- [ ] 3. 重构中
  - [ ] 3.1 新建目标 **vn** 实现路径，与**源代码**及需保留的 **v1…v(n-1)** 并存，保留回滚开关
  - [ ] 3.2 新增或实质修改的 API、类、函数补全中文注释
  - [ ] 3.3 禁止改动无关文件；若必须触碰，列出原因并告知用户
- [ ] 4. 重构后（输出报告前）
  - [ ] 4.1 《测试用例》与实现一一落地
  - [ ] 4.2 全部测试全量通过（粘贴命令与摘要）⚠️ REQUIRED
  - [ ] 4.3 校对三文档、调用图与终版实现；不一致先修订并写修订原因
- [ ] 5. 《重构报告》→ refactor/{模块名}/{vn}/重构报告.md（模板：references/重构报告模板.md）
```

撰写步骤 2.3–2.5 时按需加载 `references/技术方案模板.md`、`references/重构计划模板.md`、`references/测试用例模板.md`。

## CONFIRMATION GATE ⚠️ REQUIRED

完成步骤 2 后**停止**，输出：

> 重构前交付物已齐全：现状与风险、调用关系图、技术方案、重构计划、测试用例。路径如下：…  
> 是否确认开始写代码？(yes / no)

收到明确 `yes`（或等价肯定）前，不得创建或修改任何业务实现源代码。

## 文档骨架（写文档时必含字段）

- **技术方案**：背景与目标、范围与非范围、**基线策略**（仅源代码 / 源代码+参考 v{n}，必写清 n 与路径）、对外契约、目标结构、相对源代码与相对参考版（若有）的差异点、回滚策略、风险与缓解。
- **重构计划**：里程碑、每步输入/输出/验证、依赖与排期占位、回滚点。
- **测试用例**：编号、覆盖契约项、输入、期望输出、**按基线策略**的等价断言（仅源代码锚点，或源代码+v{n} 双线）、自动化命令。
- **重构报告**：基本信息、目标与范围、调用关系与影响、实施与 SOLID、安全/质量/性能、测试结果、等价验证结论、确认与归档、遗留项。

## SOLID 与设计

高内聚低耦合；以接口/抽象隔离 vn 与上游；新代码默认单一职责，跨职责拆到协作类。

## Red Flags（出现即停下并说明）

- 无法一段话复述职责、不变量与对外契约即写代码。
- 顺手改无关文件或全仓「整理」。
- 未更新调用图/影响范围却在旧实现上堆「更优雅」分支。
- 说不清哪条用例证明哪一入口新旧等价即推合入。
- 已存在落地 v1…却**只用源代码或只盯目标 vn 单锚**对照，导致与另一锚点漂移且无文档。
- 以「更清晰」为由改条件顺序、默认值或错误语义且未落文档与用例。
- 测试未全过即写《重构报告》或建议归档。
- 方案/用例/报告与代码、测试文件不一致且未修订。

## 反模式

- 在**源代码（原模块）**路径中原地大改后声称等价。
- 「顺手优化」与重构混在同一 commit。
- 「跑通主流程」代替全量测试通过。
- 《测试用例》事后补丁式对齐实现。
- 无回滚开关或无 vn 目录即发布。

## 交付前自检

- [ ] refactor/{模块名}/{vn}/ 含三主文档、references/（现状与风险、调用关系图）、重构报告.md
- [ ] 新增或修改的 API、类、函数均有中文注释
- [ ] 测试命令与结果已附（可写在重构报告中），全量通过
- [ ] **源代码模块**未被覆盖或误删；回滚开关明确可验证
- [ ] 《技术方案》已写明**基线策略**（仅源代码 / 源代码+参考 v{n}），与《测试用例》《重构报告》一致
- [ ] 调用关系图（Mermaid）与终版代码一致
- [ ] 技术方案、计划、用例、报告之间无静默漂移
