IRON LAW：**未复述职责且双文档未获用户明确确认前，0 行业务实现代码；确认后仍须最小改动，禁止顺带改无关文件。**

# refactor-feature-addition — 存量模块新增功能

## Iron Law（铁律）

**最小改动 + 不顺手改无关代码。**

- 以最小变更面交付新能力；能新建类/函数/策略就不要在长函数里继续堆分支。
- 动手前须理解原模块职责、上下游调用链与影响范围。
- 新增或实质修改的代码须有**中文注释**，并有单元测试覆盖**新行为**。
- 禁止以「顺便」「一劳永逸」「统一风格」为由改动与本次需求无关的逻辑、命名或全仓格式化。

## 执行前自问（写入技术方案或回复摘要）

- 不做新能力时，原有主路径的输入/输出/错误语义是否应保持不变？哪些点允许变化、为何？
- 新能力的最小挂载点是哪一处？为何不是改既有大分支？
- 必须回归的上下游路径有哪些？哪些路径应明确列为「不应受影响」？

## 前置依赖 ⛔ BLOCKING

在支持插件的 Claude Code 环境中，优先用 `understand-anything` 完成代码理解。若未安装：

```bash
/plugin marketplace add Lum1104/Understand-Anything
/plugin install understand-anything
```

安装后执行 `/understand`（或项目约定等价命令），再继续。

无插件环境：在回复中列出已读关键路径/文件与仍不确定项，**不得**跳过理解直接改代码。

## 工作流 Checklist

复制并逐项勾选：

```
- [ ] 0. 代码理解 ⛔ BLOCKING（understand-anything 或等价）
- [ ] 1. 一段话复述原模块职责、不变量、对外契约（写入技术方案 §1）⚠️ REQUIRED
- [ ] 2. 上下游调用链与影响范围（Mermaid + 文字；范围大时加载 references/影响范围模板.md）
- [ ] 3. 双文档
  - [ ] 3.1 《技术方案》→ feature/{模块名}/技术方案.md（按 references/技术方案模板.md）
  - [ ] 3.2 《测试用例》→ feature/{模块名}/测试用例.md（按 references/测试用例模板.md）
  - [ ] 3.3 CONFIRMATION GATE ⚠️ REQUIRED：未得明确肯定前禁止改业务实现代码
- [ ] 4. 实现
  - [ ] 4.1 仅改必要文件；若触碰额外文件，在技术方案「最小改动证据」列出并告知用户
  - [ ] 4.2 新增/修改的 API、类、函数补齐中文注释
  - [ ] 4.3 编写或更新覆盖新行为的单元测试（不以「只跑主流程」代替全量单测）
- [ ] 5. 验证
  - [ ] 5.1 单元测试全量通过（粘贴命令与摘要输出）⚠️ REQUIRED
  - [ ] 5.2 回归与本需求相关的上下游（测试文档中有 RG 条）
- [ ] 6. 校对：终版代码 ↔ 技术方案 ↔ 测试用例；不一致先改文档并简述原因
```

## CONFIRMATION GATE ⚠️ REQUIRED

步骤 3 完成后**停止**，输出：

> 《技术方案》《测试用例》已生成，路径如下：…  
> 是否确认开始写代码？(yes / no)

收到明确 `yes`（或等价肯定）前，不得修改实现代码（含「先改一行」）。

## SOLID 与设计

高内聚低耦合；优先扩展而非改核心分支。若改既有条件、默认值或错误语义：技术方案写明理由与兼容策略，并同步测试用例。

## Red Flags（停下并说明）

- 无法复述职责、不变量、契约即写代码。
- 无「最小改动证据」表或与 diff 不符。
- 无关文件改动或大范围无关格式化。
- 改判断顺序/默认值/错误语义未进文档与用例。
- 单测未全过即推合入。
- 代码与双文档不一致且未修订。

## 反模式

- 大范围重构 + 新功能同一 PR。
- 手工主流程代替单测全绿。
- 先实现再倒补测试对齐代码。
- 插新分支不补注释、不落测试映射。

## 交付前自检

- [ ] feature/{模块名}/ 下含技术方案与测试用例（项目另有约定则在方案中注明）
- [ ] 「最小改动证据」与 diff 一致
- [ ] 新增或修改的 API/类/函数有中文注释
- [ ] 单测命令与结果已附，全量通过
- [ ] 无无关改动（含无关依赖升级）
- [ ] 代码 ↔ 技术方案 ↔ 测试用例 一致
