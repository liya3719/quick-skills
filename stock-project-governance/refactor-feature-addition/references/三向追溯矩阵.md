# 三向追溯矩阵（需求拆解 ↔ 技术方案 ↔ 测试用例）

## 何时加载

Step 5.5 互验前**必读**；Step 6 确认门须附矩阵摘要。

## 目标

防止三文档漂移：每条 REQ 在设计、用例、计划中可双向追溯。

## 主矩阵模板

写入 `{artifactRoot}/需求拆解.md` 末尾，或 `{artifactRoot}/技术方案.md` 附录：

| REQ | 需求摘要 | 技术方案锚点（§/小节） | 研发 TC | QA TC/RG | 实施计划切片 | 状态 |
|-----|----------|------------------------|---------|----------|--------------|------|
| REQ-001 | … | §4.2 / 接口 Foo | RD-TC-01 | QA-TC-01 | Slice-1 | OK |
| REQ-002 | … | §4.3 | RD-TC-02, RD-TC-03 | QA-TC-02 | Slice-2 | BLOCKED → OPEN-001 |

**状态**：`OK` / `BLOCKED`（须引用 OPEN-xxx）/ `N/A`（须写理由）

## 互验规则 ⛔

逐项自问，任一项为否则**回到对应 Step 补文档**：

1. 《需求拆解》中每个本迭代 REQ 是否都在矩阵有一行？
2. 矩阵「技术方案锚点」列是否能在《技术方案》正文 Ctrl+F 找到？
3. 矩阵「研发 TC」列是否能在《测试用例》§ 研发视角找到对应用例 ID？
4. 矩阵「QA TC/RG」列是否能在《测试用例》§ QA 视角找到？
5. 矩阵「实施计划切片」是否能在《实施计划》找到对应条目？
6. 是否存在**仅有 TC 无 REQ** 或**仅有设计无 REQ** 的 orphan？

## REQ 手写最低字段（未安装 quick-requirement-decomposition 时）

每条 REQ 须含：

```markdown
### REQ-001 {标题}
- **意图**：一句话
- **触发/主体**：谁、在什么条件下
- **期望结果**：可观察
- **范围边界**：非目标
- **研发触点**：模块/接口/状态（非完整设计）
- **QA 线索**：Given-When-Then 或验收清单
- **依赖**：REQ-xxx 或 无
```

## OPEN 处理

| 情况 | 动作 |
|------|------|
| REQ 不可测 | TC 标 BLOCKED，引用 OPEN-xxx |
| 设计待产品确认 | 技术方案标「假设 A」，OPEN 列出 |
| 用户要求按假设推进 | Step 6 确认门显式列出假设 |

## 禁止

- 用「相关需求」「整体功能」代替 REQ 编号
- 矩阵有空行却宣称互验通过
- 三文档 REQ 编号不一致（须统一以《需求拆解》为准）
