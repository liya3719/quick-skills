# 研发技术方案

IRON LAW：**每一条实现层面的承诺（行为、接口、错误语义、数据、性能指标、边界行为）必须能对应到拆解文档中的 REQ 编号（或显式标记为「工程补充」并说明理由）。** 禁止在方案中默默发明产品逻辑或接口字段。

**版本铁律：当 PRD 或拆解稿相对上一版发生变更、或技术方案需要修订时，禁止仅在「原技术方案文件」上直接覆盖成最新内容。** 必须产出**可区分的版本**（新文件名或 `versions/` 下新文件），旧版保留可查；新版文内须说明**上一版标识**与**本版相对上一版的模块/REQ 级变更**（**与拆解 §9.2 一一对应**），使研发能一眼看出「哪些功能模块变了」。增量细则见 `references/incremental-on-req-change.md`。

**三向铁律：方案附录 D 的 REQ 变更须与拆解 §9.2 一致；交付前加载 `references/three-way-traceability.md` 互验。用例增量升版须在文档头记录「研发确认」之后进行**（见 `incremental-on-req-change.md` 确认门）。

**子方案铁律：采用「总方案 + 多份子方案」时，每一份 `{功能描述}-版本.md` 的 REQ 子集须在**总方案附录 F**中登记；子方案内仍须具备完整的追溯矩阵（仅覆盖本子集），且性能与边界章节不可省略（无 REQ 时须写「无定量 NFR」等显式陈述 + 工程补充）。**

Red Flags（若出现则回到「输入清点」步骤）：

- 拆解文档里未出现的业务规则出现在方案正文中，且无 REQ 或「工程补充」标注。
- **性能与容量**或**边界与异常场景**整章缺失、或仅有形容词无可验证标准。
- 全文找不到可追溯表格或 REQ 锚点，无法回答「这条代码对应哪条需求」。
- 接口/错误码/状态机只有笼统描述，无法用于实现或对照线上日志。
- 需求已变，但仍用「单文件原地改」且未升版号、无变更明细表（无法区分历史与当前）。
- 附录 D 与拆解 **§9.2 REQ 变更清单**不一致。
- 研发未确认方案即推动用例终稿升版。
- 已拆分多份子方案但总方案无**附录 F 子方案索引**，或子方案文件名不符合 `{功能描述}-版本.md`。

## Workflow

复制本清单并在执行中逐项勾选：

```
研发技术方案 Progress:

- [ ] Step 1: 输入清点 ⛔ BLOCKING
  - [ ] 1.1 已获取「拆解后的需求文档」版本与路径；若 PRD/拆解有变更，已读 **§9.2 REQ 变更**并对照 PRD 快照 diff
  - [ ] 1.2 列出本方案覆盖的 REQ 清单；标注 OPEN/BLOCKED 项
  - [ ] 1.3 若存在未关闭的 BLOCKED，与用户确认是暂停还是按假设推进
  - [ ] 1.4 **是否存在已交付的上一版技术方案？** 若有：记录其版本号/文件名；本版必须为**新版本**（见版本铁律）
  - [ ] 1.5 **若拆解为升版**：加载 `references/incremental-on-req-change.md`，确认增量撰写范围（仅变更 REQ 写全量设计）
- [ ] Step 2: 范围与假设确认 ⚠️ REQUIRED
  - [ ] 2.1 向用户确认：范围（REQ 列表）、非目标、关键假设
  - [ ] 2.2 **交付形态**：**单文件全量方案** / **总方案 + 多份子方案**（按拆解稿功能域拆分）；若选子方案：加载 `references/sub-design-split.md`
  - [ ] 2.3 **子方案命名预确认**（仅当 2.2 选子方案）：列出拟用的 `{功能描述}-版本.md` 列表与每份覆盖的 REQ；**取得用户确认后再撰写**（见下方确认门）
  - [ ] 2.4 确认输出形式：完整方案 / 仅增量章节（若用户指定）
  - [ ] 2.5 若有上一版方案：确认本版 **semver 或项目约定版本号**（如 v1.0 → v1.1）及**落盘文件名/路径**
- [ ] Step 3: 撰写技术方案正文
  - [ ] 3.1 加载 `references/document-outline.md`，按大纲取舍章节（不删「附录 A」；有上一版时**必填「版本与变更」与附录 D**；拆分时**必填附录 F**）
  - [ ] 3.2 **性能与容量**、**边界与异常场景**：逐条锚定 REQ 或「工程补充」（见 document-outline 对应章节说明）
  - [ ] 3.3 模块设计、接口、状态机处强制写明 REQ 引用
  - [ ] 3.4 写「可观测性」「错误与降级」以便事后对照线上
  - [ ] 3.5 **Mermaid 图示**（见下文「Mermaid 图示约定」）：按方案范围选用架构图或流程图
- [ ] Step 4: 三向互验与交付
  - [ ] 4.1 加载 `references/three-way-traceability.md`，填写附录 G（或与拆解 §11 共用 trace 文件）
  - [ ] 4.2 执行本文「Pre-Delivery Checklist」
  - [ ] 4.3 交付附：追溯矩阵、OPEN 处理方式；升版附附录 D；**发起研发确认门**（见下方）
- [ ] Step 5: 研发确认后 → 用例增量（条件）⚠️
  - [ ] 5.1 文档头记录「研发确认：日期/确认人/方案版本」
  - [ ] 5.2 指引执行 `quick-requirement-testcase-trace`：基线用例只读，新建文件，变更对照对齐 §9.2 + 附录 D
  - [ ] 5.3 用例交付后回填三向矩阵 TC 列
```

## 确认门（Confirmation Gates）

在继续之前**停下来请用户明确同意**：

- **子方案文件列表与命名**：拟生成的每一份 `{功能描述}-版本.md` 名称、路径、REQ 子集；用户确认前不批量落盘。
- **覆盖旧版或删除既有方案文件**：任何覆盖、删除、重命名已入库的技术方案文件。
- **在未关闭 BLOCKED 的前提下写死接口/枚举**：需用户书面选择「按假设 A 推进」或「暂停该 REQ」。
- **方案升版交付（终稿前）**：向研发/用户确认附录 D 与拆解 §9.2 一致、变更设计可实施；**确认前不启动用例终稿升版**。
- **研发已确认后**：在方案文档头写入确认记录，再指引 `quick-requirement-testcase-trace` 增量升版。

## Step 1: 输入清点 ⛔ BLOCKING

Ask：

- 拆解文档里 **本迭代要交付的 REQ** 是哪些？是否已有稳定编号（如 REQ-001）？
- 哪些条目在拆解文档中仍是 OPEN 或待确认？本方案是否允许「假设 A」？
- **是否已有上一版技术方案或已评审过的方案文件？** 若有：本输出是 **首次 v1.0** 还是 **升版**？升版时上一版路径/版本号是？
- **是否按功能拆成多份子设计？** 若是：每个功能域对应的 REQ 子集是否已清晰？

若无拆解文档、仅有原始 PRD：先说明无法执行本技能所要求的追溯闭环，建议先完成需求拆解或与用户约定临时编号规则后再写方案。

## Step 2: 范围与假设确认 ⚠️ REQUIRED

向用户一次性列出待确认项（尽量短）：

- 范围：REQ 列表与非目标。
- 假设：依赖第三方、开关默认值、兼容策略等。
- **交付形态**：单文件 / 总方案 + `{功能描述}-版本.md` 子方案；若子方案：**确认文件名列表**（见确认门）。
- 交付形态：新建独立文档 / 追加到某路径 / 仅输出部分章节。
- **升版时**：新版本文件名或目录约定；版本号规则（如 v1.0.0 或 v1.1）。

⚠️ 未取得用户对范围与 OPEN 项处理方式的确认前，不写定稿级接口细节（可避免返工）。

## Step 3: 撰写技术方案正文

- 加载 **`references/document-outline.md`**，按项目实际情况省略无关章，但 **附录 A 需求追溯矩阵** 不可省略；**性能与容量**、**边界与异常场景** 两章按 outline 要求落实（不可整块留空）。
- **拆分为多份子方案时**：先加载 **`references/sub-design-split.md`**，总方案写全链路架构与子方案索引；各子方案写流程、性能、边界、子集追溯矩阵。
- **存在上一版方案时**：在文档头或「版本与变更追溯」中写明 **上一版版本号、文件名、对应需求文档版本**；并填写 **附录 D 本版变更明细（按模块或 REQ）**，**REQ 列表须与拆解 §9.2 完全一致**；未变模块可引用上一版锚点。研发应能只看附录 D 即知「哪些模块动了」。加载 `references/incremental-on-req-change.md`。
- 正文建议用 **REQ 编号作小节标题或表格列**，便于 Ctrl+F 与事后排障。
- 针对「后续 AI 写代码」：对每条核心 REQ，写清 **输入/输出、边界条件、错误码、与现有代码的挂载点**；避免只写形容词。
- 针对「bug 时检索方案」：**决策**、**非目标**、**状态机**、**错误码** 单独成段或小节，避免散落在叙述里。

### Mermaid 图示约定

按**技术方案覆盖范围**选择图示类型（均使用 Mermaid，便于与 Markdown 同库维护）：

| 方案范围 | 必选图示 | 说明 |
|----------|----------|------|
| **整条需求 / 全量拆解稿**（多模块、端到端） | **架构图** | 置于「总体设计」或等价章节：系统分层、服务/客户端/外部依赖关系（如 `flowchart`/`graph` 表达边界，或 C4 风格的简化子图）。 |
| **单个功能模块（如仅 P0 某一模块或少量 REQ）** | **流程图** | 置于该模块设计小节：主路径、分支、异常/降级与关键状态转移（如 `flowchart TD/LR`、`stateDiagram` 与流程图配合）。 |

**不要求**在同一文档中重复：全量方案以架构图为主，模块内细节可用文字 + 表格；单模块方案以流程图为主，必要时补一张极简上下文架构小图以免孤立。**若用户指定**「只要流程图」或「只要架构图」，以用户为准。

**升版落盘约定（默认，可与用户改）**：新版本使用**新文件**（例如 `tech-solution-v1.1.md`），或 `tech-solution/versions/v1.1.md`；**勿**把旧版文件内容整体替换成新版且仍沿用旧文件名而不标版本——除非团队明确采用「单文件 + 文内版本历史」策略，此时文内必须保留**版本历史小节**与每次的模块级变更摘要。

**子方案文件命名（默认）**：`{功能描述}-版本.md`，细则见 `references/sub-design-split.md`。

## Step 4: 三向互验与交付

- 加载 `references/three-way-traceability.md`；附录 G 与拆解 §11 对齐（REQ 编号、变更类型、锚点）。
- 执行 Pre-Delivery Checklist；升版时附附录 D 可读性自检。

## Step 5: 研发确认后 → 用例增量（条件）

**仅当**需求变更链需要回归用例时：

1. 完成 Step 4 后**暂停**，走「研发确认门」（见确认门）。
2. 确认后在方案文档头写：**研发确认：{日期} / {确认人} / {方案版本}**。
3. 执行 `quick-requirement-testcase-trace`：`docs/testcase/` **新建**用例文件；基线只读；变更对照区对齐拆解 §9.2 + 本方案附录 D；**仅对变更 REQ** 增改废 TC，未变 REQ 引用基线 TC。
4. 用例终稿落盘后，更新三向矩阵 TC 列，状态改 `OK`。

## 交付说明

交付物默认：**中文** Markdown（除非用户指定其他格式）。首段用 3～5 句执行摘要：范围、关键架构选择、主要风险；**升版时**首段或摘要须点明「相对上一版的主要变更」。

## Anti-Patterns

- 全量方案无 **Mermaid 架构图**，或单模块方案无 **Mermaid 流程图**（与「Mermaid 图示约定」不符）。
- **性能与容量**无 REQ/工程补充锚点，或**边界与异常场景**缺失 / 仅泛泛而谈。
- 把技术方案写成 PRD 复述或口号，没有模块边界与契约。
- 接口字段、枚举、错误码不写死，用「适当处理」「优化体验」代替。
- 忽略拆解文档中的非功能需求（性能、埋点、兼容）若其存在于 REQ 中。
- 追溯矩阵用「整个系统」一行概括，或 REQ 列留空。
- 为凑篇幅添加与实现无关的通用知识（如大段语言语法）。
- 需求或 PRD 已变，仍原地改同一方案文件且不升版、不附模块级变更表（研发无法区分历史承诺）。
- 附录 D REQ 列表与拆解 §9.2 **不一致**（多/少/类型不符）。
- 跳过研发确认门，直接发布用例终稿。
- 拆分子方案却缺少总方案**附录 F**，或子方案追溯矩阵与总方案 REQ 分配**矛盾**。

## Pre-Delivery Checklist

### 结构与追溯

- [ ] 文首或文档头中能读到：**覆盖的 REQ 列表**与拆解文档版本
- [ ] 附录中存在 **REQ → 设计要点 → 章节/锚点** 的追溯矩阵，且与正文相互印证
- [ ] 拆解文档中的 P0 REQ 在方案中均有对应设计（或显式说明延期与风险）
- [ ] **若存在上一版技术方案**：本版有**独立版本标识**；旧版未被静默覆盖；**附录 D** 与拆解 **§9.2** REQ 级变更**一致**
- [ ] **三向互验**：附录 G（或共用 trace 文件）已填；变更 REQ 有方案锚点；用例未就绪标 `待用例`
- [ ] **若拆分子方案**：总方案含 **附录 F**，且每份子方案文件名符合 **`{功能描述}-版本.md`**；子方案附录 A 为 REQ 子集且与总方案一致

### 性能与边界

- [ ] **性能与容量**章：有 **REQ/NFR 引用**或可验证指标，或显式「无定量 NFR」+ **工程补充**默认
- [ ] **边界与异常场景**章：有 **表格或列表**，场景与 **REQ/工程补充** 对齐，覆盖拆解稿相关异常与边界（无则显式说明）

### 可实施性

- [ ] 关键接口或契约以 **可实现的粒度** 写出（字段级或等价表格）
- [ ] 异常与降级路径有描述，且可与日志/埋点关键词对应
- [ ] 无未解释的 `[TODO]`、`TBD`、`待定`（若必须有，集中在「风险与未决事项」并标责任人或时限）

### 图示（Mermaid）

- [ ] **全量需求级方案**：正文含至少一张 **架构图**（Mermaid），与「总体设计」一致
- [ ] **单功能模块 / 单模块 P0 方案**：正文含与该模块相关的 **流程图**（Mermaid），覆盖主路径与关键分支

### 语言

- [ ] 正文主体为 **中文**；标识符、API 路径、错误码保持与代码一致的原样拼写
- [ ] **观测可扫描**：确认门列出本方案覆盖 REQ 数；附录 A/D 标题可被 `quick-pipeline-observability` 解析（见其 metric-dictionary 别名）
