# 需求变更后的技术方案增量迭代

> **何时加载**：Step 1 发现拆解稿相对上一版有 §9.2 REQ 变更；或用户声明「PRD/拆解已升版」。

## 前置 ⛔

- 已存在**新版本拆解**（新建文件，非覆盖旧拆解）。
- 已读拆解 **§9.1–§9.2**（PRD 快照引用、REQ 级变更清单）。
- **禁止**在未读 §9.2 的情况下重写方案正文。

## 增量撰写策略

1. **新建方案文件**（如 `tech-solution-v1.1.md` 或 `{功能}-v1.1.md`）；**保留**上一版文件只读。
2. **文档头**：关联需求 = **新拆解**路径+版本；「上一版方案」= 基线路径。
3. **附录 D**（必填）：每一行与拆解 §9.2 **REQ 一一对应**：

| 模块/子系统 | 涉及 REQ | 相对上一版 | 摘要 |
|-------------|----------|------------|------|
| （与 §9.2 变更类型一致） | REQ-003 | 修改 | … |

4. **正文**：
   - **新增/修改 REQ**：写完整设计（模块、接口、边界、性能锚点）。
   - **无变化 REQ**：可写「设计同 `{上一版方案}` §x.y，本版未触及」+ 锚点；**禁止**静默改接口/行为却不标「修改」。
   - **废弃 REQ**：在范围章注明废弃，附录 D 标 `删除`，不写新实现细节。
5. **附录 A 追溯矩阵**：覆盖本方案声明的全部 REQ；变更 REQ 更新「设计要点/章节锚点」列。

## 与 PRD 快照链

文档头或「版本与变更追溯」写明：

- 上游拆解版本 → 拆解引用的 **PRD 快照**路径
- 本方案相对上一方案，因哪次 **PRD/REQ 变更**而升版（一句话）

## 研发确认门 ⛔（方案交付后、用例升版前）

方案初稿完成后**暂停**，向研发/用户确认：

- 附录 D 与拆解 §9.2 是否一致
- 变更 REQ 的设计是否可实施
- 确认后：在方案文档头或 §10 写 **「研发确认：日期 / 确认人 / 本版方案版本」**

**未确认前**：

- 不得将方案标为终稿
- **不得**启动 `quick-requirement-testcase-trace` 的用例升版（可起草 TC 清单但不落终稿）

## 确认后 → 测试用例增量

指引执行 `quick-requirement-testcase-trace`：

- 基线用例 = `docs/testcase/` 上一版（只读）
- 新建用例文件，变更对照区对齐拆解 §9.2 + 方案附录 D
- 仅对**变更 REQ** 新增/修改/废弃 TC；未变 REQ 可引用基线 TC 编号
- 完成后更新 `references/three-way-traceability.md` 矩阵

## 禁止

- 原地覆盖旧方案文件充当 v1.1
- 附录 D 与拆解 §9.2 REQ 列表不一致
- 研发未确认即发布用例终稿
