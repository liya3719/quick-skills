# 子设计任务拆分（总方案 + 多份子方案）

加载时机：用户要求「按功能拆分子设计」、覆盖 REQ 较多需并行评审、或 Step 2 确认采用「总方案 + 子方案」交付时通读本文件；撰写单文件全量方案时可不加载。

## 何时拆分

- 拆解稿中**多个相对独立的功能域**（不同页面/服务/子系统），各自有清晰 REQ 子集。
- 需要**多人并行**撰写或评审，单文件过长不利于 diff 与责任边界。
- 用户明确要求按「需求描述的功能」拆成多份设计任务。

**不强行拆分**：单一连贯流程、强耦合状态机、共享同一数据模型且无法划界时，用**一份**方案 + 模块小节即可。

## 文件命名（强制）

- 格式：**`{功能描述}-版本.md`**
  - **`{功能描述}`**：与拆解文档中的功能/模块名称一致，**简短可读**；使用中文或团队约定英文 slug；**禁止** `/`、`\`、`:` 等路径非法字符。
  - **`版本`**：与**总方案主版本对齐**（如总方案为 v1.0，子方案可为 `子功能模块功能-v1.0.md`），或项目统一 semver；**同一迭代内多份子方案版本号应一致**，便于检索。
- 示例：`测评结果与报告-v1.0.md`。

## 总方案（母文档）必须包含

- 文档头注明：**交付形态 = 总方案 + N 份子方案**；列出各子方案**文件名**。
- **附录 F：子方案索引**（见 `document-outline.md`）：每行对应一份 `{功能描述}-版本.md`，列明**覆盖 REQ**、文件路径、一句话摘要。
- **总体设计**仍保留**一张 Mermaid 架构图**（全链路上下文）；子方案不得与总架构矛盾。

## 单份子方案必须包含

与 `document-outline.md` 同结构**按需取舍**，但以下**不可省略**：

| 区块 | 要求 |
|------|------|
| 文档头 | 关联**总方案文件名与版本**、本份覆盖的 **REQ 列表**、拆解稿版本 |
| 模块与责任 / 流程 | **Mermaid 流程图**（本子集主路径 + 关键分支） |
| **性能与容量** | 对齐拆解稿/NFR：**指标或阈值**（响应时间、并发、包体等）或显式写「本 REQ 无定量 NFR，按系统默认」并给**工程补充**理由 |
| **边界与异常场景** | 表或列表：**场景** → **预期行为** → **REQ/工程补充**（空数据、重复提交、超时、权限、弱网等） |
| 附录 A | **需求追溯矩阵**（仅本文件覆盖的 REQ 子集） |

升版时：子方案遵循与总方案相同的**版本铁律**（新文件名或 `versions/`，旧版保留）；总方案附录 F、附录 D 同步更新。

## 追溯关系

- 子方案附录 A 的 REQ 必须是总方案附录 A 的**子集**；总方案附录 A 可一行汇总「详见子方案 X」并指向对应章节锚点。
- 实现排障时：**REQ → 先查总方案附录 A → 再定位子方案文件名与锚点**。
