# PRD 快照对照与增量拆解

> **何时加载**：Step 1 存在历史拆解或 PRD 变更；Step 6 非首版交付前**必读**。

## 目标

对照**不可变 PRD 快照**产出**新版本拆解**（新建文件），研发能回答：相对上一版 PRD/拆解，**哪些 REQ 变了、为何变**。

## 对照流程 ⛔

1. **定位快照对**：
   - **基线 PRD**：上一版拆解文档头「上游 PRD 快照」路径（只读）。
   - **当前 PRD**：本次定稿；**先**落盘 `docs/prd/_snapshots/{需求名}-prd-v{N}-{YYYYMMDD}.md`，**禁止**覆盖旧快照。
2. **结构化 diff**（按章节/功能块，非逐字 diff 即可）：
   - 新增 / 删除 / 修改的**业务能力**、验收口径、NFR、范围边界。
   - 标注来源：快照章节 ↔ 新 PRD 章节（或段落摘要）。
3. **映射到 REQ**（写入新版 §9.2）：

| PRD diff 类型 | REQ 动作 |
|---------------|----------|
| 新能力 | 新增 `REQ-0xx` |
| 口径/范围变更 | **保留编号**，变更类型 `修改`，写旧→新 |
| 能力下线 | `废弃`，写替代 REQ 或从哪版起不实现 |
| 仅措辞润色、验收不变 | 可不升 REQ；在 §9.1 变更摘要一句带过 |

4. **正文撰写策略**：
   - **修改/新增 REQ**：在本版 §5 写**完整现行**三视图（见 `output-template.md`）。
   - **未变 REQ**：正文仍写全量（便于单文件阅读），或在 §9.2 备注「与继承版一致」且继承版路径明确——**禁止**静默改未标「修改」的 REQ 正文。
5. **新建拆解文件**：`docs/prd/{需求名}-v{x.y}.md`；文档头「继承自」填上一版路径。

## 增量摘要（给研发一眼读 diff）

在新版 §9.1「变更摘要」用 3～5 条 bullet：

- 业务动机（为何升版）
- 受影响模块/域
- 新增/修改/废弃 REQ 计数
- 是否影响已上线行为（兼容/迁移）

## 下游衔接（写入 §10 或文档头）

| 下游产物 | 本版拆解交付后 |
|----------|----------------|
| 技术方案 | 引用本拆解版本；方案须**新建**版本文件，附录 D 对齐 §9.2 |
| 测试用例 | **待研发确认技术方案后**再升版；用例新版本引用本拆解 + 已确认方案版本 |
| 三向矩阵 | 加载 `three-way-traceability.md`，在拆解文末附矩阵（至少覆盖变更 REQ） |

## 禁止

- 无 PRD 快照 diff 表，仅口头说「PRD 变了」就重写拆解
- 在旧拆解文件内改 REQ 却不升版本
- 修改 REQ 正文却不写入 §9.2 变更清单
