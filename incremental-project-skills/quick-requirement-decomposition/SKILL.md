# 产品需求拆解

**语言**：本 Skill 产出的说明、表格与清单默认使用**中文**；保留 REQ-xxx、OPEN-xxx、BLOCKED、N/A 等结构化标记不变。

IRON LAW：禁止把含糊表述当作已验证需求交付。每个原子 REQ 必须要么对应至少一条可观察的测试线索，要么在「待澄清」中列出并带 OPEN-xxx 编号——不得用乐观措辞掩盖不确定性。

IRON LAW（版本）：**原始 PRD 变更后，禁止在历史拆解文档正文中直接覆盖成新版内容**（避免研发无法区分「曾承诺过什么」与「现在写什么」）。须保留原始 PRD 快照、为拆解文档递增版本并记录 REQ 级变更；实现代码所依据的拆解版本必须在文档头或团队约定的 `CHANGELOG` 中可查询。细则见 `references/versioning.md`。

## 工作流

复制下列清单并在完成时勾选：

```
产品需求拆解进度：

- [ ] 步骤 1：摄入并归一输入 ⚠️ REQUIRED
  - [ ] 1.1 区分目标 vs 既定方案 vs 示例
  - [ ] 1.2 标注约束、非功能、风险与未知项
  - [ ] 1.3 若存在历史拆解：定位上一版拆解文件与对应 PRD 快照，准备做「差异拆解」而非覆盖旧文件
- [ ] 步骤 2：原子化并分配 REQ 编号 ⚠️ REQUIRED
  - [ ] 2.1 每条 REQ 只含一条能力或规则；合并段落需拆分
  - [ ] 2.2 标明 REQ 间依赖
- [ ] 步骤 3：为每条 REQ 填写三视图 ⚠️ REQUIRED
  - [ ] 3.1 大模型视图：意图、语义、消歧
  - [ ] 3.2 研发视图：边界、触点、数据/状态流、风险
  - [ ] 3.3 QA 视图：验收、异常与边界、NFR 检查或 BLOCKED
- [ ] 步骤 4：追溯矩阵与待澄清项 ⚠️ REQUIRED
- [ ] 步骤 5：确认门 ⚠️ REQUIRED
- [ ] 步骤 6：交付结构化产物（含版本元数据、变更记录；见 output-template 第 1/9 节）
```

## 步骤 1：摄入并归一输入 ⚠️ REQUIRED

自问：

- 脱离任何界面或接口草图，业务要达成的结果是什么？
- 哪些表述是强制实现、哪些只是可协商示例？
- 明确不在范围内的有哪些？

将材料归类为：业务目标、用户场景、功能行为、约束、非功能、集成、风险、待澄清。

若输入混杂多类模式（流程 + 权限 + 集成），注明将拆分。选择如何拆分时加载 `references/decomposition-patterns.md`。

## 步骤 2：原子化并分配 REQ 编号 ⚠️ REQUIRED

规则：

- 全文使用稳定编号：REQ-001、REQ-002、…
- 每条 REQ 写明：主体（角色或系统）、触发条件、期望结果、范围边界
- 若两条验收可独立执行，应拆成两条 REQ；除非一条是另一条的下位规则（则在依赖中注明父子关系）

## 步骤 3：为每条 REQ 填写三视图 ⚠️ REQUIRED

对每条 REQ 补全三视图：

- **大模型**：一句话意图；语义上的输入输出；易混点
- **研发**：边界；涉及系统；数据或状态流；风险与待验证点——不是完整详细设计
- **QA**：Given-When-Then 或等价清单；负面与边界；NFR。尚不可测时，测试线索填 BLOCKED 并引用 OPEN-xxx

撰写终稿时加载 `references/output-template.md` 以统一字段名与章节顺序。

## 步骤 4：追溯矩阵与待澄清项 ⚠️ REQUIRED

按 `references/output-template.md` 建矩阵：每行 REQ 须标明大模型、研发、QA 三列是否已满足，或显式 N/A 及原因。

未知项合并为 OPEN-001、OPEN-002、…，并列出受影响的 REQ 编号。

## 步骤 5：确认门 ⚠️ REQUIRED

暂停并向用户呈现：

- 范围与非目标摘要
- REQ 条数与 OPEN 条数
- 可能影响架构或测试范围的假设

询问：是否按现状继续、缩小范围、或先澄清部分 OPEN。

在用户确认前，勿将长文标为终稿；若用户明确要求跳过确认以节省时间，可例外。

## 步骤 6：交付结构化产物

按 `references/output-template.md` 输出全文。优先单份连贯文档，而非三份互不关联的列表。

**首次拆解**：在 `docs/prd/_snapshots/`（或团队约定目录）保存一份**原始 PRD 不可变快照**，拆解正文文件名带版本（如 `需求名-v0.1.md`），文档头填写「上游 PRD 快照」与「拆解文档版本」。

**PRD 变更后再拆解**：

1. 再存一份新的 PRD 快照（新文件名，不覆盖旧快照）。
2. **新建**拆解文件 `需求名-v0.2.md`（或递增规则见 `references/versioning.md`），**不要**把 `v0.1` 文件改写为新版内容。
3. 在新拆解中增加「版本与变更记录」：相对上一版，哪些 REQ 新增/修改/废弃，差异摘要；并更新追溯矩阵中受影响行。
4. 在聚合 `CHANGELOG` 或文档头中写明**代码实现基线**将指向本版（分支/tag/工单与研发约定一致）。

加载 `references/versioning.md` 获取命名、目录与 REQ 编号变更策略。

## 反模式

- 仅把 PRD 改写得更好听，却没有原子编号与测试线索
- 为回避冲突把不兼容目标塞进同一条 REQ
- 研发视图只有空话（可扩展、稳健）而无边界与触点
- QA 只有主路径，NFR 一笔带过
- 用「体验好」「好用」等掩盖歧义而不列 OPEN
- 在多条 REQ 下重复同一验收却不说明重复或合并理由
- **PRD 变更后在同一拆解文件内静默改字、不升版本、不保留 PRD 快照与 REQ 差异表**（研发无法对齐代码与验收）

## 交付前自检

- [ ] 每条 REQ 有 REQ-xxx 编号，三视图已填或 N/A 有理由
- [ ] 每条 REQ 有测试线索，或为 BLOCKED 且引用 OPEN
- [ ] 追溯矩阵无空行，除非该格为 N/A 并写明原因
- [ ] 术语表覆盖易混产品术语
- [ ] 无残留占位：TODO、FIXME、TBD、xxx（刻意留在待澄清列表的除外）
- [ ] 待澄清列表覆盖所有未解决的歧义
- [ ] **版本**：文档头含拆解版本、上游 PRD 快照引用；若非首版，含「版本与变更记录」且 REQ 级变更可追溯
- [ ] **实现基线**：已约定本版与研发分支/tag/工单的对应方式（见 `versioning.md`）
