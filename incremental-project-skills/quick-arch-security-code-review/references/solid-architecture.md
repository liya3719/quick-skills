# SOLID 与架构审查（提问清单）

> 在 Step 2 中按需加载。用具体问题替代笼统评价。

## Single Responsibility（单一职责）

- 问：这个模块/类若需求变更，会有几种互不相干的原因需要改它？超过一种 → 考虑拆分。
- 问：函数名是否描述**一件事**？若用「和/与」才说得清，可能职责过多。

## Open/Closed（开闭）

- 问：新增一种类型/策略时，是否**必须**修改现有 `switch` 或长 `if-else`？若否，是否可通过扩展新类/插件/策略注册完成？

## Liskov 替换

- 问：子类是否**收紧**了父类契约（例如抛新异常、返回更窄类型）？调用方以父类类型使用时会否被破坏？

## Interface Segregation（接口隔离）

- 问：接口是否包含调用方**从不使用**的方法？若实现类要留空或抛 `NotImplementedError`，可能接口过大。

## Dependency Inversion（依赖倒置）

- 问：高层模块是否**直接**依赖具体实现类？是否应依赖抽象（接口/协议）与注入？

## 分层与边界

- 问：业务逻辑是否混在 **Controller/UI** 或 **SQL 构建** 中？数据访问、领域规则、表示层是否可区分？
- 问：跨层是否出现 **循环依赖** 或 **包级反模式**（如 util 被一切引用又引用一切）？

## 可测试性

- 问：核心逻辑能否在**不启动完整应用/不连真实库**下单测？若不能，常因**硬编码依赖**或**静态全局**。
