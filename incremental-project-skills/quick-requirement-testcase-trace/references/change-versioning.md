# 需求变更时的用例文档策略（增量版本）

## 何时用本文件

当**原始 PRD 或拆解需求发生变更**（增删改 REQ、改验收口径、改范围）且已存在一版用例文档时：**禁止**在原用例文件正文里直接覆盖成新版终稿。

## IRON 规则（与 SKILL 正文一致）

- **保留基线文件**：历史用例文档保持只读归档语义；新版本**新建独立 Markdown 文件**。
- **新版本必须自洽**：新文件内包含完整可用的用例集（可以是全量复制后改，或「基线 + 增量」——若选增量，须明确基线文件与合并方式，避免执行测试时缺表）。

## 新文件命名与路径

**目录（固定）**：`docs/testcase/`

**文件名**：`{产品或模块}-testcases-v{主版本}.{次版本}-{简述}-{YYYYMMDD}.md`

`{产品或模块}-testcases-v{主版本}.{次版本}-{简述}-{YYYYMMDD}.md`

## 新文件文档头（在 testcase-doc-template 元数据之外追加）

| 字段 | 说明 |
|------|------|
| 本文档性质 | 固定写「需求变更增量 / 用例 vX.Y」 |
| 基线用例文档 | 上一版用例文件的**路径与版本号** |
| 覆盖的需求变更 | 对应 PRD/拆解的**版本或变更单** |
| 关联 REQ 变更 | 列出受影响 REQ-xxx；新增 REQ 注明「新增」 |
| 关联技术/任务变更（可选） | 子方案增删、附录 F 变更、子任务/任务包重分域；简写或表格一行 |

## 变更对照区（必填，放在文档前部）

### 1. 需求变更点摘要

逐条列出（可用表格）：

| 编号 | 涉及 REQ | 变更前（摘要） | 变更后（摘要） | 来源（PRD/拆解 章节或版本） |

### 2. 用例变更点摘要

| 编号 | TC 编号 | 变更类型 | 说明 |
|------|---------|----------|------|
| | | 新增 / 修改 / 废弃 / 合并 / 拆分 | |

### 3. 原始用例 vs 本次变更（逐条或按 TC）

对**每一条**受影响的 TC，至少给出：

- **原始用例**：从基线文档摘抄或引用「TC 编号 + 标题 + 关键步骤/预期」（足够复现对比即可，不必全文粘贴若基线可访问）。
- **本次变更内容**：明确写新增字段、步骤、预期差异或「本 TC 废弃，由 TC-xxx 替代」。

若变更面大，可写「全量差异见附录 A」，但附录 A 仍须满足「可追溯、可 diff」——禁止只写「已按新需求更新」而无对照。

## 矩阵更新

在新文件中更新「需求—用例追溯矩阵」：废弃的 TC 在说明列标 `deprecated` 及替代 TC；新增 REQ 须有对应 TC 或 BLOCKED 说明。若团队已采用**功能 / 异常 / 边界**三层主表列（见 `testcase-doc-template.md`），升版时须同步更新「用例层级」「关联功能用例」，避免派生关系断裂。

## 与拆解 skill 的配合

若团队使用 `quick-requirement-decomposition`：REQ 编号应与拆解稿一致；需求变更时拆解稿亦应**升版而非覆盖**，用例新版本引用**拆解新版本**的 REQ 基线与 **§9.2 变更清单**。

## 与方案确认门（BLOCKING）

**用例升版前**须满足：

1. 关联技术方案为**新版本**（非覆盖旧文件）。
2. 方案文档头含 **「研发确认：日期 / 确认人 / 方案版本」**（由 `quick-tech-solution` Step 5 写入）。
3. 无确认记录时：可起草 TC 清单，**不得**将 `docs/testcase/` 新文件标为终稿。

用例变更对照区的「涉及 REQ 变更」须与拆解 §9.2、方案附录 D **一致**。

## 三向互验

用例交付后：更新拆解 §11 / 方案附录 G 的 TC 列；执行 `quick-requirement-decomposition/references/three-way-traceability.md` 互验规则。
