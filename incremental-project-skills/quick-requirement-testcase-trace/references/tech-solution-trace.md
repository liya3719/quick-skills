# 技术方案、子方案与子任务（测试侧如何衔接）

加载时机：项目已按 **总方案 + 附录 F 子方案索引** 或 **子任务拆分**（见 `quick-req-driven-codegen` 的 `references/architecture-and-task-split.md`）落地时；需要把用例与**研发任务包、回归范围、并行测试**对齐时通读本节。

## 与 REQ 的关系（不可颠倒）

- **验收与「是否测到需求」仍只认 REQ-xxx**：每条 TC 的**主追溯**须是 REQ；子方案文件名、子任务编号为**辅助字段**，便于排期与选例，**不能**作为「零 REQ 绑定」的借口。
- 若某条子任务/子方案在方案中**未覆盖任何 REQ**（仅工程债）：用例可标 `N/A`+说明，或单独记 OPEN；不得假装对应产品 REQ。

## 文档与矩阵里多写什么（均为可选）

1. **文档头**（见 `testcase-doc-template.md`）：补「对应总方案 / 子方案范围」路径与版本，与方案升版时同步更新用例**新版本文件**（见 `change-versioning.md`），不覆盖旧用例单文件当终稿。
2. **用例主表**（可选列）：`关联子方案`（`{功能}-vX.Y.md` 或锚点）、`关联子任务/任务包`（若团队有任务表 ID 或方案内任务行号——**以用户给出的真源为准**，不自造编号）。
3. **需求—用例矩阵**：在「缺口说明」外，可增加一列 **主要涉及子方案**（多对多时写「见主表」），用于按子域做**选择性回归**。

## 与方案变更的同步

- 总方案**附录 F** 增删子方案、或 REQ 在子方案间**迁域**：用例**升版**时在新文件的「变更对照区」或矩阵中写清**受影响的子方案/任务包**；TC 的 REQ 列优先更新，子方案列随之改。
- **禁止**：仅因「子任务完成了」就宣称 REQ 已验收——仍须步骤/预期能落到 REQ 的验收口径。

## Anti-patterns

- 用例标题/步骤里只写「验证子任务 T3」而无 REQ 编号。
- 子方案与磁盘文件、附录 F 不一致时，用例里写死子方案名却不标 BLOCKED/OPEN。
