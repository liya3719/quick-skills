# 需求追溯测试用例

**语言**：说明、表格与清单默认使用**中文**；保留 REQ-xxx、TC-xxx、OPEN-xxx、BLOCKED、N/A 等结构化标记不变。

IRON LAW（输出路径）：**用例终稿必须写入仓库 `docs/testcase/` 目录**（路径相对于项目根）。禁止写到聊天临时路径或未约定目录。文件名见 `references/change-versioning.md`；确认门前向用户给出**完整相对路径**。

IRON LAW：**禁止在「需求已变更」的场景下直接改写旧版用例文件正文以充当最新终稿。** 必须**新建**独立用例文档，并在其中写明需求变更点、用例变更点、原始用例是什么、本次变更是什么；旧文件保留为基线。

IRON LAW：**禁止交付「零 REQ 绑定」的用例终稿。** 每条 TC 须至少对应一条 REQ-xxx；无法绑定时标 BLOCKED 并引用 OPEN-xxx，不得用语义模糊的「相关需求」代替编号。

IRON LAW：**子方案、子任务（开发任务包）仅作工程辅助信息**（排期、并行、分域回归）；**不得**用「只绑子任务/子方案、不绑 REQ」代替验收追溯。若填写关联子方案/子任务，须与 `rd-tech-solution` 附录 F 及总方案版本一致，不自造任务编号。

IRON LAW（三层输出）：**须按「功能 → 异常 → 边界」分层交付**，主表「用例层级」与「关联功能用例」列必填（见 `references/testcase-doc-template.md`）。**异常/边界 TC 必须能追溯到具体功能 TC**（派生关系写清）；禁止把异常/边界混在功能 TC 的步骤里却不标层级、不标派生来源。

IRON LAW（层级可视化）：**每条 TC 必须在 mermaid 图中有且仅有一处叶子节点**（一 REQ 一图，默认 **`flowchart TB`**，固定三层分支：功能用例 / 异常用例 / 边界用例）；格式见 `references/mindmap-per-testcase.md`。**禁止**在 Markdown 用例终稿中默认使用 `mindmap`（Cursor/VS Code 内置预览常无法渲染）。禁止仅有表格而无图，或图与主表 TC 编号/层级矛盾。

Red Flags（若出现则回到「确认输入与基线」步骤）：

- 准备保存时才发现没有拆解稿或 REQ 列表。
- 想偷懒「直接改上次的用例文件」省一个文件名。
- 用例步骤里全是笼统操作，无法与某条 REQ 的验收口径对齐。
- 技术方案为「总方案 + 多份子方案」或已拆子任务，但用例文档**未**记录总方案/附录 F 路径（或用户确认「本迭代不测分域」）却仍写子方案名。
- 以「子任务/开发单完成」代替 REQ 级验收，步骤中无 REQ 可对齐的实质检查点。
- 异常/边界 TC 成群出现但**关联功能用例**列为空或指向不存在的功能 TC。
- 主表已写满 TC，正文却**没有任何 mermaid 图**，或若干 REQ 的 TC 未出现在对应 REQ 的图叶子中。
- 用例写毕却保存在 `docs/testcase/` 之外，或文件名与版本策略不一致。
- 需求变更链上**方案未研发确认**却发布用例终稿。

## 输出位置 ⚠️ REQUIRED

| 项 | 约定 |
|----|------|
| 目录 | **`docs/testcase/`**（不存在则创建） |
| 命名 | `{产品或模块}-testcases-v{主}.{次}[-{简述}]-{YYYYMMDD}.md` |
| 示例 | `docs/testcase/需求名-testcases-v0.1.md` |
| 升版 | **新建**文件，不覆盖旧文件；基线路径写在变更对照区 |

## 工作流

复制下列清单并在完成时勾选：

```
需求追溯测试用例进度：

- [ ] 步骤 1：确认输入与基线 ⚠️ REQUIRED
  - [ ] 1.0 ⛔ BLOCKING：无拆解稿或无法列出 REQ-xxx 时，先补拆解或取得用户临时编号规则；不得输出宣称「可验收」的用例终稿
  - [ ] 1.1 定位原始 PRD 与拆解需求路径、版本、日期
  - [ ] 1.2 列出本任务覆盖的 REQ-xxx；标注是否有 OPEN-xxx 阻塞
  - [ ] 1.3 确认输出目录为 **`docs/testcase/`**，拟定本任务文件名（含版本号）
  - [ ] 1.4 若为用例升版：定位**基线用例文档**（只读，须在 `docs/testcase/`），禁止在未建新文件前编辑基线
  - [ ] 1.5 ⛔ **方案确认门**（需求变更链）：关联技术方案须已**研发确认**（文档头「研发确认：…」）；无确认则仅可草案，不落终稿
  - [ ] 1.6（条件）项目存在**总方案 + 附录 F 子方案**或**子任务/任务包表**：记录总方案路径、版本；子方案文件列表或任务包与 REQ 的对应关系；若本迭代不区分分域/任务，用户确认后可略写
- [ ] 步骤 2：选择文档策略 ⚠️ REQUIRED
  - [ ] 2.1 初版 / 全量：加载 references/testcase-doc-template.md
  - [ ] 2.2 需求已变更且存在旧用例：加载 references/change-versioning.md，**新建**文件名并写变更对照区
- [ ] 步骤 3：编写或合并用例 ⚠️ REQUIRED
  - [ ] 3.1 建用例主表与（推荐）追溯矩阵（列定义见 `references/testcase-doc-template.md` 含三层列）
  - [ ] 3.2 **功能层**：以 REQ 或拆解中的核心流为锚，每锚点 **2～3 条**正常场景 TC；步骤覆盖**完整主路径**；填**优先级**；层级标「功能」，「关联功能用例」填「—」
  - [ ] 3.3 **异常层**：逐条对照 3.2 的功能 TC，推导异常分支（缺参、类型错误、权限不足、资源不存在、业务规则冲突、状态不允许操作等）；层级标「异常」，**关联功能用例**填对应功能 TC 编号
  - [ ] 3.4 **边界层**：在功能主路径上补充空值/最大最小/特殊字符与超长/并发与重复提交/超时/跨模块联动等；层级标「边界」，**关联功能用例**填对应功能 TC；不适用的 REQ 在矩阵「缺口说明」写 N/A 与理由
  - [ ] 3.5 每条 TC 填写**追溯 REQ**；覆盖缺口或阻塞显式写出
  - [ ] 3.6 加载 references/mindmap-per-testcase.md：主表定稿后，为**每个 REQ** 写 `### REQ-xxx` 小节并附 **`flowchart TB`**（模块→REQ→功能/异常/边界→TC 叶子；主表每条 TC 恰出现一次）
  - [ ] 3.7 将完整用例文档**写入** `docs/testcase/{拟定文件名}.md`
  - [ ] 3.8（条件）已执行 1.5：加载 references/tech-solution-trace.md，为主表/矩阵**可选**增加子方案或子任务列；REQ 列仍必填
- [ ] 步骤 4：确认门 ⚠️ REQUIRED
  - [ ] 向用户呈现：REQ 覆盖摘要、OPEN/BLOCKED、若为升版则呈现「原始 vs 本次变更」要点
  - [ ]（条件）有子方案/子任务：说明按哪几份子方案或任务包可做**选择性回归**（与 REQ/TC 的对应关系）
- [ ] 步骤 5：预交付自检（见文末清单）
```

## 步骤 1：确认输入与基线 ⚠️ REQUIRED

自问：

- 当前 authoritative 的拆解版本是哪一个文件？REQ 编号是否连续、是否与 PRD 冲突？
- 是否存在上一版用例文档？若有，路径与版本号是什么？
- 总方案/附录 F/子任务是否已存在？若存在，用例元数据与可选列是否与其**版本与 REQ 分配**一致？

若为**需求变更后的用例升版**：把基线用例文档视为只读参照；新版本输出为**另一个文件**。

## 步骤 2：选择文档策略 ⚠️ REQUIRED

- **首次编写或全量替换**：按 `references/testcase-doc-template.md` 建章节与元数据。
- **需求变更、已有旧用例**：按 `references/change-versioning.md` 新建文件，在文首写「变更对照区」，再给出完整可执行用例集（或基线合并策略须写清，避免测试执行缺项）。

## 步骤 3：编写或合并用例 ⚠️ REQUIRED

**生成顺序**：先完成功能层（黄金路径与 2～3 条正常变体），再为每条功能 TC 派生异常层，最后补边界层。详细枚举与列说明见 `references/testcase-doc-template.md` 中「三层用例生成约定」。

对每条 REQ，自问：

- **功能**：是否有 2～3 条可执行 TC 覆盖该 REQ 的主验收口径与关键变体（角色/数据/入口差异）？
- **异常**：每条功能 TC 是否已有对应异常分支表或显式写「本流无接口层异常」等可辩护的 N/A？
- **边界**：该 REQ 涉及的输入域、状态机、IO 与跨模块触点是否有点名边界 TC 或矩阵中说明推迟？

用例字段优先级：**追溯 REQ**、**用例层级**、**关联功能用例**、**可执行步骤** 先于文风修饰；**关联子方案/子任务**在 REQ 与步骤已立住之后再填（无方案拆分时整列可省略）。

**层级可视化**：主表行定稿后，按 REQ 生成 `flowchart TB` 三层总览（先写表再画图）。编排与示例见 `references/mindmap-per-testcase.md`。

技术方案中已有**子任务拆分**时：仍按 REQ 组织覆盖；子任务只帮助标「本 TC 更贴近哪一开发包/哪份子方案」——见 `references/tech-solution-trace.md`。

## 步骤 4：确认门 ⚠️ REQUIRED

暂停并向用户呈现：

- 覆盖的 REQ 条数与缺口的 TC 或 BLOCKED 说明
- **三层摘要**：各 REQ 下功能 TC 数量、由之派生的异常/边界条数；若某层刻意裁剪，说明范围约定
- **mindMap / 层级图覆盖**：主表 TC 条数 = 全部 REQ 图叶子总数；每个 REQ 的三层分支齐全（可抽检 1～2 个 REQ 核对与主表一致）
- 若为升版：列出将**废弃 / 替代**的 TC 编号及原因
- 若发现拆解与 PRD 不一致：不擅自定稿，列出待产品确认项
- **输出路径**：`docs/testcase/` 下本文件的完整相对路径

在用户确认范围与文件名策略前，不要将内容冒充为团队已接受的终稿（若用户仅要求草稿，须在文档头注明「草案」）。

## Anti-Patterns

- 在用例正文里写「详见需求」却不给 REQ 编号。
- 需求变更后只发一段文字 diff，不新建用例文件、不保留「原始用例 vs 本次变更」对照。
- 复制粘贴基线全文到新文件却不更新元数据、矩阵与变更对照区，导致版本语义混乱。
- 为凑覆盖率写无法执行的步骤或与 REQ 无关的冗余 TC。
- 用例仅对齐子任务标题或 Jira 单号，不落到 REQ-xxx 与可验证预期。
- 子方案/附录 F 与磁盘文件不一致，在用例中照抄过期的子方案文件名不标注风险。
- **只有功能 happy path**，无异常/边界层或未在矩阵说明推迟原因。
- **异常/边界 TC 未填写「关联功能用例」**，或层级与「类型」列自相矛盾。
- **把 2～3 个正常场景挤在一条 TC 的步骤里**却不拆成多条功能 TC（除非用户明确要求合并为场景表）。
- **只交付主表、不写层级图**，或图缺「功能用例 / 异常用例 / 边界用例」三层分支，或主表 TC 未全部出现在对应 REQ 的叶子中。
- **在 Markdown 终稿中默认写 `mindmap`** 导致预览环境无法渲染（应改用 `flowchart TB`）。

## Pre-Delivery Checklist

### 追溯与结构

- [ ] 每条 TC 至少绑定一个 REQ-xxx，或 BLOCKED+OPEN-xxx
- [ ] 主表含**用例层级**（功能/异常/边界）与**关联功能用例**；异常/边界行的关联列指向有效功能 TC
- [ ] **每条 TC 在 REQ 级 flowchart 中有叶子节点**（全文件叶子数 = 主表 TC 数）；每 REQ 一图、三层分支齐全；叶子编号/层级/标题与主表无矛盾
- [ ] 每个覆盖范围内的 REQ 至少 **2～3 条功能层 TC**，或文档/确认门说明刻意收窄理由
- [ ] 存在需求—用例矩阵或等价说明，缺口有交代；可选增加「各层 TC 计数」一行摘要
- [ ] 若为升版：新文件已写清基线文档路径、需求变更点、用例变更点、原始用例与本次变更
- [ ] 若使用子方案/子任务列：与当前总方案、附录 F（及任务表若存在）一致，且无「仅有子任务、无 REQ」的 TC

### 质量

- [ ] 无占位符（TODO/FIXME/xxx）留在宣称「可执行」的用例步骤中
- [ ] 文档头元数据完整（见 template / change-versioning）

### 禁止项复查

- [ ] 未在「需求已变更」场景下仅覆盖旧用例文件作为唯一真相源
- [ ] 终稿已落在 **`docs/testcase/`**，且确认门给出的路径与实际文件一致
