# 输入物料与研发确认门禁

## 何时加载

步骤 2 **必读**；未 pass → **⛔ BLOCKING**，禁止进入步骤 4（执行计划）之后的任何业务代码编辑。

## 目录约定 ⛔

| 物料 | 根目录 | 典型路径 | 来源 skill |
|------|--------|----------|------------|
| **需求拆解** | `docs/` | `docs/prd/{需求名}-v{x.y}.md` | `quick-requirement-decomposition` |
| **技术方案** | `docs/` | `docs/design/{需求名}-tech-solution-v{x.y}.md`；子方案 `{功能描述}-v{x.y}.md` | `quick-tech-solution` |
| **设计数据** | `design/` | `design/{需求名}/*.json`（结构）、`*.png`（视觉）、token、manifest |

**禁止混淆**：`docs/design/` 是**技术方案 Markdown**；**`design/`**（项目根）是**设计工具可解析数据**，二者不可互换。

## 齐套检查（整齐）

- [ ] 三类物料**均已 Read**；路径、版本号写入执行计划元数据
- [ ] 拆解 REQ 列表与方案附录 A / 设计分块**版本一致**（同一 `{需求名}-v{x.y}` 链）
- [ ] 方案每个 UI 相关设计分块，在 `design/` 有配对 `*.json` + `*.png`（或已标 `UI-N/A` + OPEN）
- [ ] 无散落聊天/飞书链接替代仓库内固定文件
- [ ] OPEN / BLOCKED / TBD 已汇总；**未关闭 BLOCKED 且无用户确认** → 整单 blocked
- [ ] 项目规则（`AGENTS.md` / `CLAUDE.md`）存在则已 Read

## 研发确认 ⛔

三类物料**均须研发确认**后方可编码。确认记录优先读文档/manifest；无记录则**停下来走确认门**。

| 物料 | 确认记录位置 | 格式示例 |
|------|--------------|----------|
| 需求拆解 | 文档头或 §10 | `研发确认：2026-04-20 / 张三 / v0.2` |
| 技术方案 | 文档头（`quick-tech-solution` 约定） | `研发确认：2026-04-21 / 李四 / tech-solution-v1.1` |
| 设计数据 | `design/{需求名}/manifest.md` 或 README | `研发确认：2026-04-22 / 王五 / design-v1.0` |

| 缺失时 | 动作 |
|--------|------|
| 拆解无确认 | **blocked**；请用户确认或补写文档头 |
| 方案无确认 | **blocked**；须先完成 `quick-tech-solution` 研发确认门 |
| 设计数据无确认（UI 相关 REQ） | **blocked**；禁止写 UI |
| 设计数据无确认（纯逻辑、UI-N/A） | 可继续，执行计划标 `UI-N/A` + 用户确认 |

## 版本对齐自问

- 拆解版本 ↔ 方案文首「上游拆解版本」是否一致？
- 方案版本 ↔ 执行计划元数据是否一致？
- `design/` manifest 版本 ↔ 方案引用的设计稿版本是否一致？

任一不一致 → 标 OPEN，**不得标 ready block**。

## 禁止

- 跳过本门禁直接写业务代码
- 仅有 PNG 无 JSON、或仅有 JSON 无 PNG 却写 UI
- 方案仍为草案/TBD 密集却按终稿编码
- 用旧版拆解配新版方案（或反之）且无 OPEN 说明

## 降级（须用户书面确认）

- **仅逻辑层、无 UI**：`design/` 可标 `UI-N/A`；仍须拆解 + 方案研发确认
- **设计数据滞后**：用户确认「先实现非 UI block」→ 仅 ready 且无 UI 证据的 block 可编码
