# 整体架构与子任务拆分

加载时机：用户要基于 **PRD + 技术方案（含总方案与子方案索引）** 先做**整体架构设计**，再按**子方案**分任务开发；或多份子方案并行落地、需统一边界与顺序时通读本文件。单文件方案、且总方案已含冻结的架构图与附录 F 时，可只核对不重复造文档。

## 输入须已具备（与 SKILL.md 步骤 1 对齐）

- **PRD** 或等价产品输入：路径与版本（若 REQ 拆解已吸收 PRD 要点，可注明「以拆解稿为准」并给拆解版本）。
- **总方案**：含**总体架构**（至少一张全链路 Mermaid 或等价图）、**附录 F 子方案索引**（子方案文件名、路径、覆盖 REQ、摘要）。
- **各子方案**：`{功能描述}-版本.md`，与附录 F 一致；单份内 REQ 子集、模块责任、接口与边界已在方案中写明。

若总方案缺附录 F 或子方案列表与磁盘文件不一致，**先对齐或记入 OPEN**，再画架构、拆任务。

## 整体架构设计（产出什么）

在 **PRD + 总方案 + 附录 F** 约束下，整理或补全一份**一页内可读完**的架构视图（可用 Mermaid），至少明确：

1. **系统上下文**：终端/渠道、外部系统、与本项目边界的输入输出（与方案一致，不新增系统）。
2. **逻辑分层或模块边界**：与总方案图一致；命名与方案/子方案标题对齐。
3. **跨模块集成点**：API/事件/路由/共享状态在**哪两份子方案或 REQ** 中约定；无约定则 **OPEN**，不自造契约。
4. **与 REQ 的映射**：架构块或箭头旁标注 **REQ-xxx**（来自拆解/方案附录 A），便于后续分任务追溯。

**禁止**：在子方案未覆盖的模块间「发明」职责划分、同步协议或数据所有者。**允许**：为落实已有方案而写的「工程补充」（标注理由）。

## 确认门（架构冻结）

在以下情况，**输出架构草稿后暂停**，用户确认或修订后再进入子任务拆分与编码：

- 首次多子方案联调、或总方案架构图与当前代码仓目录结构差异大。
- 识别出子方案之间的**依赖环**或**REQ 归属冲突**。

## 子任务拆分（按子方案）

1. **任务粒度**：默认 **一子方案 → 一个开发任务包**（含该子方案覆盖的 REQ、主要文件/服务边界）；若单份子方案过大，按方案内「模块」或 REQ 批次再拆，但须在任务表注明父级子方案文件名。
2. **依赖排序**：  
   - 先实现被依赖的契约（类型、API mock、共享组件）若总方案/子方案已规定顺序。  
   - 无显式顺序时，按 **数据流上游 → 下游** 与 **阻塞集成点优先** 排列；不确定则 **OPEN** 并问用户。
3. **并行度**：无依赖关系的任务包可标为「可并行」；有共享分支的须 **串行或先合并契约**。
4. **每任务包出口**：列出「应对齐的子方案章节」「REQ-xxx 列表」「建议 TC 或自测点」；不替代编码步骤中的 token/契约检查。

## 与 rd-tech-solution 的衔接

- 子方案命名、附录 F、总方案与子方案追溯关系以 **`rd-tech-solution` 与子设计拆分约定**为准；本 reference 不重新定义文件名规则。
- 若用户仅在实现阶段进入本 skill，**以磁盘上的总方案 + 子方案为准**，不以对话记忆为准。

## Anti-patterns

- 总方案已有冻结架构图，仍重写一套与之冲突的「新架构」。
- 子任务按人头随意分，**忽略子方案内流程顺序与 REQ 依赖**。
- 架构图中出现方案未出现的中间层或存储，且未标工程补充或 OPEN。
