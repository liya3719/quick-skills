# 语义抽检 Rubric（L3）

> **何时加载**：确认门前填写 `human` 段；每条抽中的 REQ 独立打分。

**规则**：每题 **0 或 1**（不适用标 `N/A` 并写理由，不计入分母）。汇总写入 metrics：

- `human.capability_loss_rate` = 未覆盖能力点数 / 评审能力点总数（能力点清单由产品/评审提供，可附在报告）
- `human.atomicity_pass_rate` = 原子性题得 1 的 REQ 数 / 抽检 REQ 数
- `human.rubric_samples` = 抽检明细数组（可选）

禁止用「整体感觉良好」代替下表。

---

## 每条抽中 REQ 的五问

| ID | 问题 | 1 的标准 | 0 的典型 |
|----|------|----------|----------|
| R1 | **原子性** | 一条能力/规则；验收可独立执行 | 多能力捆一条；应拆未拆 |
| R2 | **可观察验收** | Given-When-Then 或检查项可客观判定 | 「体验好」「合理」无观察点 |
| R3 | **方案锚点真对应** | 方案 § 锚点打开后内容服务本 REQ | 锚点空、错章、或仅标题匹配 |
| R4 | **实现/计划覆盖** | 执行计划或对齐报告有 block 挂本 REQ，或显式 N/A | 无映射却宣称完成 |
| R5 | **TC 可证伪** | 至少一条功能 TC 步骤能证伪错误实现 | 步骤含「详见需求」/TODO；或仅绑子任务无 REQ |

**单条 REQ 合格**：R1–R2 必须为 1；R3–R5 在对应下游已存在时必须为 1，否则标 N/A。

---

## 能力点丢失（整需求一次）

1. 评审列出本迭代 **must-have 能力点**（建议 10～30 条，来自 PRD）。
2. 逐条对账：是否存在主路径验收覆盖该点的 REQ。
3. `capability_loss_rate = 未覆盖数 / 能力点总数`。
